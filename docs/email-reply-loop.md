# 邮件回复闭环

## 本期范围

发送邮件 → 客户回复 → IMAP 收信 → 关联客户和邮件会话 → 写入互动记录并生成待办 → 分析客户意图 → 撰写回复 → 人工审批 → SMTP 发出 → 完成对应回复待办。

新增导航「客户邮件」，包含待回复、待关联、已处理、已发送、全部视图。可以直接在该页面审核最终收件人、正文和附件并批准发送，不需要切换到审批页。审批记录同时保留在统一审批和 Agent 运行中。

当前是一个组织一个团队收信账号，与现有组织级 SMTP 配置相配套，不是每位销售独立的私人邮箱。OWNER / ADMIN 配置并同步邮箱，MANAGER 可查看团队来信、人工关联客户，普通销售只能查看自己负责或未分配客户的邮件，VIEWER 只读。待关联的原始邮件仅向团队管理角色开放。

## 配置与验收

1. 部署 Java 后端及前端，执行 V18 数据迁移。V18 依赖 V17 的跟进功能。
2. 保留原有「设置 → 发件邮箱」SMTP 配置，先测试发信连接。
3. 在「设置 → 邮件回复接收」配置 IMAP 地址、端口、账号、授权码及文件夹，保存后测试收信。
4. 开启自动同步。默认配置未创建、同步未开启，不会读取邮箱或消耗模型 Token。
5. 在客户联系人中维护正确邮箱。从本系统审批发出一封邮件，再用客户邮箱回复。
6. 在「客户邮件」点击同步，或等待后台扫描。核对邮件正文、客户、会话和新增跟进任务。
7. 按需点击「分析客户意图」。这一步复用 Python AI 服务和个人 Token 限额；收信本身不调用模型。
8. 撰写回复，选择已上传的当前客户附件，提交审批。审核界面展示数据库保存的最终快照，批准后才真实发送。
9. 发送成功后原来信显示「已回复」，新增发信记录、客户互动记录，并完成该来信对应的待办。

IMAP 授权码复用现有 AES-GCM 主密钥加密机制，只存密文，不在接口、页面或日志中返回密码。留空可保留同账号的授权码；更换服务器或账号时必须重新输入，防止将旧密码发给新服务器。

支持 SSL/TLS（通常 993）和必须成功升级的 STARTTLS（通常 143），不支持明文密码传输，也不跳过服务器证书校验。使用 Gmail 等邮箱时，需要账号或组织允许 IMAP 与应用授权码；本期未实现 OAuth 登录。具体可用性以邮箱服务商及组织政策为准。

## 收信机制

- 首次接入选择最近 200 封邮件，分批处理，每次最多 50 封；之后按 UID 增量同步。
- 记录 UIDVALIDITY；文件夹重置或更换账号后重新定位，以 Message-ID 去重。
- 缺少有效 Message-ID 时使用账号、文件夹、UIDVALIDITY、UID 生成稳定备用标识。
- 使用只读文件夹与 PEEK，不删除邮件，不修改原邮箱已读状态。
- 同步使用数据库租约，手动同步与后台扫描不会并发领取同一账号；租约五分钟失效，可从中断中恢复。
- 在网络读取完成后按封执行短事务。互动、待办、邮件关联一起提交；同步失败不会推进游标，重读由唯一约束去重。
- 收信使用独立、有界的后台工作线程，避免慢邮箱阻塞主动跟进等其他定时任务；上批未结束时不堆积新批次。
- 网络连接、读取和写入均有超时；每批处理有软时间上限，避免长期占用扫描线程。
- 自动回复、群发通知、投递报告等只归档为忽略状态，不生成跟进任务，也不自动回复。

后台默认每 60 秒扫描，首次延迟 20 秒：

```properties
app.mail.sync-enabled=true
app.mail.sync-interval-ms=60000
app.mail.sync-initial-delay-ms=20000
```

关闭后台扫描不影响管理员手动同步。无需新增 Python 接口或依赖，IMAP 使用已有邮件依赖。

## 客户与会话匹配

优先检查 In-Reply-To / References 是否引用本组织已记录的出站邮件，同时校验来信发件人确实在原收件人列表内，来信收件地址包含原发件地址。匹配成功沿用原客户及会话。

没有可用线程引用时，按联系人邮箱精确匹配本组织的有效客户。只有唯一客户才自动关联，不按主题猜测；多个客户共用同一地址或没有匹配时进入「待关联」。人工关联后补写互动和回复待办。

上线前的老邮件没有本系统保存的 Message-ID，仍可按唯一联系人邮箱归档，但不能凭空恢复完整历史线程。

邮件头和发件人地址不是身份认证证明，IMAP 只能反映邮箱收到的内容。人工仍需核对可疑或高风险来信，不能仅凭线程匹配执行付款、改账户等操作。

## 发信与安全边界

新的系统发信统一使用 MIME 消息，并在 SMTP 调用前持久化稳定 Message-ID 与 SENDING 记录。回复加入 In-Reply-To / References，使后续来信可以归入会话。

审批提交时固定收件人、主题、正文、当前客户的附件 ID，并生成内容哈希。同一来信通过版本号和待审批/执行状态检查，阻止重复提交；发送动作也只能从 APPROVED 领取一次，不会重新领取 EXECUTING 动作。

SMTP 成功仅代表服务器接受消息，不代表客户已读或最终投递成功。本期没有邮件打开追踪，不伪造“客户已阅读”事件。

SMTP 超时、发送后数据库异常等无法判断副作用的情况，显示 UNKNOWN「发送结果需核对」，不自动重发。中断超过十分钟仍停留在 SENDING 的记录也转为 UNKNOWN。用户需先到原邮箱核实；已有未确认发送记录的来信不允许重新提交回信，避免重复触达。异常中断导致审批动作持续执行中时，需管理员核对运行记录后处理，当前不提供一键重发。

邮件 HTML 仅提取文本，前端按纯文本显示，不执行脚本、不加载远程图片。正文读取与 MIME 嵌套深度受限，超过 2MB 的整封邮件只提示到原邮箱查看。附件仅记录名称，不自动下载、执行或导入 RAG；发送附件只能从当前客户已上传文件中明确选择，最多十个。

AI 分析仍将邮件正文视为不可信数据。分析结果仅供参考，不自动发送、不自动覆盖客户字段；由用户决定后续操作。

## 验证与限制

覆盖收信去重、唯一/歧义客户匹配、自动通知过滤、正文安全解析、角色权限、凭据变更保护、SMTP 结果不确定、重复发送保护、审批与待办闭环，以及桌面/手机页面。

PostgreSQL 集成测试在独立 schema 中执行 V1、V17、V18，验证真实 Mapper SQL、邮件入库、互动/任务生成、审批、发送记录和完成待办，测试结束回滚：

```powershell
$env:MAIL_TEST_DB_URL='jdbc:postgresql://127.0.0.1:55433/postgres'
cd backend
.\mvnw.cmd -o -Dtest=MailPostgresTests test
```

自动测试不使用真实企业邮箱、不向外发送邮件。上线后仍需用实际邮箱完成一轮上述收发验收，确认防火墙、IMAP 权限、授权码和 SMTP 策略可用。
